Semua pintasan pembayaran mengarah ke Angsuran dan unggah bukti transfer; invoice Xendit tertunda yang sudah ada tetap dapat dibuka dari notifikasinya, sementara webhook dipertahankan untuk mencatat callback lama dan meneruskan callback aplikasi lain.)

## 2. Google Drive — Struktur & Efek

### 2.1 Struktur folder

Semua berkas siswa tersimpan di **akun Google pemilik aplikasi** (`vworksofficial@gmail.com`), kuota 15GB gratis akun tersebut. OAuth bertindak sebagai pemilik file, sehingga kuota service account (0 byte) tidak menjadi masalah.

```
My Drive (vworksofficial@gmail.com)
└── VSV.VentureGo.id [database]/               ← ROOT (sebelumnya `VentureGo Berkas`, di-rename in-place)
    ├── Budi Santoso - LPK Sakura/             ← folder DRAFT, warna MERAH (menunggu persetujuan)
    │   ├── KTP - Budi Santoso.pdf
    │   └── Pas Foto - Budi Santoso.jpg
    ├── VSV-0001-2026 - Budi Santoso/          ← siswa resmi (status ACTIVE): rename + warna HIJAU
    │   ├── KTP - Budi Santoso.pdf
    │   └── KK (Kartu Keluarga) - Budi Santoso.jpg
    └── Siti Rahayu - LPK Harapan/             ← pemohon lain (folder terpisah per Firebase UID)
```

- **Root** `VSV.VentureGo.id [database]`: dibuat otomatis oleh aplikasi di root My Drive (scope `drive.file` — aplikasi hanya melihat file buatannya sendiri). Bila yang ditemukan masih bernama lama `VentureGo Berkas`, aplikasi **mengganti namanya di tempat** (folder ID dan seluruh isi tetap sama) pada akses pertama. Override opsional via env `GDRIVE_ROOT_FOLDER_ID`.
- **Satu folder per Firebase UID**: folder dibuat sekali per UID (tidak dicari berdasarkan nama), dipetakan di `driveFolders/{uid}`, dan dipakai ulang untuk semua pengajuan UID tersebut — dua siswa dengan nama & LPK sama tidak pernah berbagi folder. Saat memulai unggahan, server memeriksa bahwa folder mapping masih ada, belum masuk sampah, dan memang folder; bila referensinya sudah tidak valid, server membuat folder baru khusus UID tersebut dan memperbarui mapping. Berkas selalu berupa file langsung di dalam folder (tanpa subfolder) agar verifikasi kepemilikan saat submit tetap berlaku.
- **Folder draft (warna MERAH `#ff0000`)**: `<Nama Pemohon> - <Nama LPK>` (mis. `Budi Santoso - LPK Sakura`) — dibuat saat unggahan pertama pemohon, `stage: 'draft'`. Folder tetap merah dengan nama ini setelah pengajuan terkirim.
- **Folder siswa resmi (warna HIJAU `#00ff00`)**: saat status pengajuan menjadi **`ACTIVE`** (atau saat dokumen akad diterbitkan ketika status sudah `ACTIVE`), server (a) membaca **NIS** yang sudah diterbitkan saat terbit dokumen akad (`getExistingStudentNumber`), (b) **me-rename** folder menjadi `<NIS> - <Nama Pemohon>` (mis. `VSV-0001-2026 - Budi Santoso`), (c) mengwarnai hijau, (d) me-rename seluruh berkas di dalamnya ke pola nama standar, dan (e) memperbarui mapping `stage: 'active'`. Bila saat transisi ke `ACTIVE` NIS belum terbit, promosi ditunda hingga dokumen akad diterbitkan; perubahan status berikutnya tidak mengembalikan folder ke merah.
- **Unggahan susulan** (setelah pengajuan ada): langsung ke folder yang tercatat di `driveFolderId` aplikasi; folder dibuat bila belum ada (dengan nama & warna sesuai status aplikasi).
- **Nama file standar**: `<Jenis Dokumen> - <Nama Pemohon><ekstensi>` (mis. `KTP - Budi Santoso.pdf`, `Ijazah SMA - Budi Santoso.pdf`, `Akad Wakalah bil Ujrah - Budi Santoso.pdf`). Awalan `Scan ` dan bagian setelah `/` pada label dokumen dibuang; nama asli berkas dari pengguna tidak dipakai sebagai nama Drive.

### 2.2 Alur unggahan (chunked resumable)

1. Klien memanggil `POST /api/applicant/uploads` dengan header `x-upload-action: init` + token ID Google Firebase → server memvalidasi lalu membuat sesi resumable di Drive → mengembalikan `ticket` (HMAC, TTL 30 menit) + `chunkSize` 4 MB.
2. Klien mengirim potongan (`x-upload-action: chunk`, header `Content-Range`) — 4 MB per potongan (di bawah limit body Vercel 4,5 MB).
3. Potongan pertama **diverifikasi tanda tangan berkas** (magic byte PDF/JPG/PNG) — bila salah → sesi dibatalkan, error `Isi berkas tidak sesuai dengan formatnya.`
4. Potongan terakhir → file selesai → bila unggahan terkait pengajuan, transaksi Firestore menulis entri `documents[index]` `{documentType, status:'UPLOADED', fileId, fileName, mimeType, size}` + `driveFolderId`. Bila transaksi gagal, file di Drive **dihapus** (tidak ada file yatim).
5. Server **memverifikasi ulang** setiap `fileId` ke Drive saat submit — file yang tidak ada di folder milik pemohon akan menggugurkan pengajuan.
6. Error tak terduga pada route unggah mencatat tahap, aksi, jenis/kode error, dan ID referensi acak ke log server tanpa token, UID, nama berkas, atau isi dokumen; ID referensi ikut ditampilkan agar kegagalan localhost dapat dicocokkan dengan log.

### 2.3 Validasi & batasan

| Aturan          | Nilai                              | Pesan error (user-facing)                                                |
| --------------- | ---------------------------------- | ------------------------------------------------------------------------ |
| Tipe file       | PDF, JPG, PNG                      | `Gunakan berkas PDF, JPG, atau PNG.`                                     |
| Ukuran per file | maks **10 MB**                     | `Ukuran berkas maksimal 10 MB.` / `Ukuran setiap berkas maksimal 10 MB.` |
| Total ukuran    | maks **60 MB**                     | `Ukuran seluruh dokumen tidak boleh melebihi 60 MB.`                     |
| Isi file        | Cocok dengan ekstensi (magic byte) | `Isi berkas tidak sesuai dengan formatnya.`                              |
| Token sesi      | Harus akun Google & valid          | `Sesi unggah telah berakhir. Silakan muat ulang halaman.` (401)          |
| Ticket unggahan | HMAC, TTL 30 menit                 | `Sesi unggah tidak valid. Silakan ulangi unggahan.`                      |
| Scan KTP        | Wajib ada saat submit (2 produk)   | `Dokumen Scan KTP wajib diunggah.`                                       |

### 2.4 Efek sisi Drive saat alur berjalan

| Aksi aplikasi                               | Efek di Google Drive                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unggahan pertama (sebelum submit)           | Folder draft `<Nama> - <LPK>` **merah** dibuat di root (bila belum ada)                                                                                                                                                                                                                                                         |
| Submit pengajuan **berhasil**               | Nama/warna folder **tidak berubah** (tetap draft merah); mapping `driveFolders` → `stage:'submitted'`                                                                                                                                                                                                                           |
| Status pengajuan → **`ACTIVE`**             | Bila NIS sudah terbit: folder **di-rename** `<NIS> - <Nama>` + warna **hijau** + seluruh berkas di-rename pola `<Jenis> - <Nama>`; mapping → `stage:'active'`                                                                                                                                                                   |
| Admin menerbitkan dokumen akad (`.docx`)    | File `Akad Wakalah bil Ujrah [dan Jualah] - <Nama Pemohon>.docx` disimpan di folder pengajuan; bila status sudah `ACTIVE`, folder langsung dipromosikan ke hijau                                                                                                                                                                |
| Submit **gagal**                            | File yang baru terunggah **dihapus** otomatis (`discardDriveUploads`)                                                                                                                                                                                                                                                           |
| Ganti dokumen di unggah-berkas              | File baru ditulis dengan nama `<Jenis> - <Nama Pemohon>`; **file lama tidak dihapus** oleh sistem (lihat §8); dokumen berstatus `VERIFIED` **tidak bisa diganti** pemohon — tombol `Ganti` nonaktif dan server menolak unggahan (`409` saat init, `422` + `Dokumen sudah diverifikasi dan tidak dapat diubah.` saat finalisasi) |
| Admin mengunggah PDF akad                   | File `Akad Wakalah bil Ujrah - <Nama Pemohon>.pdf` disimpan di folder pengajuan (versi lama tetap ada)                                                                                                                                                                                                                          |
| Admin mengunduh dokumen                     | Stream dari Drive (`GET /api/admin/.../documents/[index]`), tidak ada URL publik                                                                                                                                                                                                                                                |
| Akses kedaluwarsa (token OAuth kadaluwarsa) | Error 503 `Akses penyimpanan berkas kedaluwarsa. Silakan setujui ulang akses aplikasi.`                                                                                                                                                                                                                                         |

### 2.5 Kredensial (server-only, di Vercel & `.env.local`)

- `GDRIVE_OAUTH_CLIENT_ID`, `GDRIVE_OAUTH_CLIENT_SECRET` — OAuth client tipe _Desktop app_.
- `GDRIVE_REFRESH_TOKEN` — hasil klik **Allow** sekali oleh pemilik akun; server menukarnya jadi access token otomatis.
- Consent screen harus berstatus **Production** agar refresh token tidak kedaluwarsa 7 hari.
- Tidak ada kunci service account yang dipakai lagi untuk Drive.

## 4. Alur Kerja Admin (Staf)

### Cakupan antrean Persiapan Akad dan Pengarsipan

Record kontrak Legacy (`legacy` atau `contractScheme` berawalan `LEGACY_`) tetap disimpan di Firestore sebagai riwayat kontrak, pembayaran, dan berkas siswa. Record Legacy tidak dimasukkan ke antrean kerja **Persiapan Akad** maupun **Pengarsipan** karena kedua menu tersebut menangani proses akad baru; badge jumlah di sidebar mengikuti daftar antrean yang sama. Berkas dan riwayat Legacy tetap dapat ditinjau dari data serta rincian siswa; pemisahan antrean ini tidak menghapus atau mengubah data. Status pembayaran Legacy tetap mengikuti saldo: kontrak yang masih memiliki sisa kewajiban tercatat sebagai aktif, sedangkan yang telah lunas seluruhnya tercatat sebagai alumnus.

### 4.1 Masuk `/admin`

- **Tidak ada halaman login admin terpisah.** Staf masuk lewat tombol `Masuk dengan Google` di welcome `/` memakai akun Google yang terdaftar sebagai staf (di semua mode).
- Tombol demo `Masuk User`/`Masuk Admin` **sudah dihapus**. Akun demo di `src/lib/demo-accounts.json` tetap ada untuk keperluan script/pengujian, tetapi tidak lagi punya tombol di halaman awal.

**Field rincian biaya dan isi Draft Akad:**

- Slide-over `Pratinjau Dokumen Akad` memakai header gradasi biru dengan identitas siswa, label Draft/Terbit sejajar judul (tanpa eyebrow atau kode pengajuan), area dokumen A4 di atas latar abu-abu, loading spinner dan skeleton halaman, serta tampilan error dengan tombol `Coba lagi`. Halaman PDF berupa gambar beresolusi tinggi dari pratinjau. Berkas DOCX final yang sudah diterbitkan tetap tersedia dari bagian Dokumen Akad.

Admin dapat memilih tanggal akad; tanggal di blok tanda tangan mengikuti pilihan ini. Nomor kontrak ditampilkan sebagai pratinjau read-only dengan urutan NIS otomatis, skema produk, bulan Romawi, dan tahun. Nama perwakilan LPK sebagai saksi diisi admin di samping nama wali untuk Dana Keberangkatan — bila kosong, paragraf saksi terisi `Mitra Venturego (LPK)`; bila diisi menjadi `LPK <mitra> — <nama>`; saksi Full Cover tetap mengikuti template.

Item tiket pada Pasal 2 juga dihapus bila tidak ada biaya tiket di rincian Nafaqah (label turunan otomatis tidak pernah memuat kata tiket). Tabel Lampiran A pada DOCX kini **tanpa baris header `NAFAQAH`/`UJRAH` dan tanpa baris info `Dibayarkan ke LPK (invoice)`**: **3 baris layanan Nafaqah (Pendidikan Bahasa Jepang, Pelatihan Skill Kerja, Pengurusan dokumen) digabung lewat `w:vMerge`** — baris pertama memuat penerima `LPK Mitra Venturego` dan satu nominal `Rp<nafaqahTotal>`, baris lanjutan hanya penerus `vMerge` — disusul **baris ke-4 `Uang saku` di dalam bagian Nafaqah** (baris `Qardh hasan` lama dibuang dari rincian), mengosongkan kolom Jumlah **dan penerima** baris tanpa nominal, serta menebalkan baris `Subtotal Nafaqah (termasuk uang saku)`, `Subtotal Ujrah`, dan `TOTAL KEWAJIBAN`. Pratinjau dan DOCX draft Dana Keberangkatan menurunkan rincian dari principal + invoice LPK (fallback `departureDetails.outstandingLPKAmount`) lewat `deriveDepartureFinancials`, sehingga angkanya sama dengan tabel Rincian Lampiran A di tab Draft Akad (baik DOCX maupun kartu kini menampilkan uang saku sebagai baris ke-4 bagian Nafaqah); nilai tersimpan hanya dipakai bila turunan tidak valid.
- Kartu ringkasan `Total Nafaqah (Riil)` (= invoice LPK, bukan jumlah baris), `Total Ujrah (Jasa)`, `Total Kewajiban Akad`, dan `Estimasi Angsuran / Bulan` berada di paling atas tab Draft Akad Dana Keberangkatan; kartu terpisah `Qardh − Refund` dihapus.
- Card `Rincian penggunaan dana` ditempatkan tepat di bawah baris kartu ringkasan dengan status validasi, field nominal, dan visual alur alokasi dana. Untuk Dana Keberangkatan dana bersih dihitung sebagai nominal pengajuan dikurangi admin 5%, invoice LPK dibayarkan dari dana bersih, dan sisanya otomatis menjadi uang saku. Nilai total HPP dan nominal pengajuan tidak ditampilkan sebagai kartu terpisah.

Input `Tanggal angsuran pertama`, `Refund/potongan` + bukti, dan `Catatan penyelesaian` dihapus dari UI — nilai tersimpan tetap dipertahankan saat simpan. Kartu `Ketentuan pelengkap Draft 1` dan notifikasi penyerahan qardh dihapus; penyerahan uang saku tidak lagi menjadi syarat status biaya.
- Input nominal invoice LPK dan uang saku pada `Rincian penggunaan dana` menampilkan prefix `Rp` serta pemisah ribuan titik saat diketik, sementara nilai yang disimpan tetap berupa angka; state fokus menggunakan satu outline di sekeliling field.

- **Full Cover** (hanya Jepang yang bisa diverifikasi): rincian kebutuhan di tab _Budgeting_ menjadi sumber nilai Nafaqah dan baris biaya pada Draft Akad. Biaya pendaftaran/MCU, pendidikan bahasa per bulan, uang saku bahasa per bulan, paket pelatihan skill/dokumen, uang saku skill per bulan, dan uang saku keberangkatan setelah COE dicatat sebagai enam komponen terpisah. Admin menetapkan durasi Bahasa Tahap 1 dan Skill Tahap 2 secara independen (saran awal 3 bulan untuk masing-masing); nilai durasi tersimpan sebagai snapshot anggaran, dan subtotal pendidikan serta uang saku dihitung otomatis. Total pihak ketiga + total uang saku menjadi Nafaqah. Uang saku keberangkatan masuk total Nafaqah tetapi waktu penyalurannya tetap setelah COE; Ju’alah tetap terpisah dan bersyarat COE. Ujrah, Ju’alah, tenor 1–36 bulan, dan estimasi angsuran tetap dikelola pada Draft Akad.
- **Dana Keberangkatan**: invoice tagihan LPK + uang saku siswa harus sama dengan nominal pengajuan setelah dipotong biaya admin 5%; Nafaqah harus sama dengan invoice LPK dan sisa dana bersih otomatis menjadi uang saku/qardh. HPP disimpan terpisah dari Ujrah sehingga total kewajiban akad tetap menghitung Ujrah sesuai akad. Rincian **Lampiran A bersifat tetap dan diturunkan otomatis** (helper `deriveDepartureFinancials` di `src/lib/departure-financing.ts`): Nafaqah = 3 komponen tetap (Pendidikan Bahasa Jepang, Pelatihan Skill Kerja, Pengurusan dokumen) tanpa nominal per baris — digabung lewat `w:vMerge` dengan penerima `LPK Mitra Venturego` dan satu nominal invoice di baris pertama — ditambah **baris ke-4 uang saku** dengan subtotal = invoice + uang saku, Ujrah = 2 baris turunan (wakalah 2,4% × 12 bulan + administrasi 5%, penerima `VentureGo VSV`), Uang saku = dana bersih − invoice (= qardh); staf hanya mengisi **Invoice LPK terverifikasi** (uang saku ikut terhitung, read-only) dan `Jumlah angsuran (1–36)`; referensi akad final tidak wajib diisi, sedangkan tanggal angsuran pertama, refund, dan catatan penyelesaian tidak lagi diedit dari UI (nilai tersimpan dipertahankan). Total live: `Nafaqah + Ujrah + qardh − refund` — uang saku/qardh selalu ikut dihitung dalam Total Kewajiban tanpa syarat penyerahan; ketentuan Draft 1 (bahasa 6 bln, skill 6 bln, dokumen 30 hari kerja, peringatan 3×, tenggang 7 hari) diisi otomatis nilai bawaan oleh server.

**Aturan bisnis penting saat `Simpan`** (semua memblokir dengan pesan spesifik):

- **Full Cover — sumber nominal:** `financialPlan.fullCoverBudget` menyimpan rincian enam komponen dan snapshot durasi; input durasi Bahasa Tahap 1 dan Skill Tahap 2 terpisah dengan saran awal 3 bulan dan batas 1–60 bulan. Biaya Pendidikan Bahasa Jepang Tahap 1 dimasukkan sebagai total untuk seluruh durasi (misalnya Rp8.000.000 untuk 3 bulan, tanpa dikalikan lagi); hanya uang saku bahasa/skill yang dihitung dari nominal bulanan × durasi. Usulan awal uang saku bahasa/skill Rp1.000.000 per bulan dan uang saku keberangkatan Rp3.300.000 dapat disunting sebelum disetujui. Kartu Ringkasan Alokasi Pembiayaan menampilkan total Nafaqah, Ujrah Wakalah, Ju’alah, input tenor (bawaan 18 bulan; rentang 1–36), dan estimasi angsuran; Ujrah Wakalah diturunkan 10% dari Nafaqah serta Ju’alah 50% tanpa menampilkan persentase di UI. Rincian terverifikasi masuk ke `offerSnapshot` / `financialPlanHistory`; perubahan setelah `AGREED` membatalkan referensi persetujuan lama dan mengembalikan status ke `VERIFIED`.

Field alamat pada Identitas dan tanggal akad menggunakan textarea tinggi dan membentang sepanjang dua baris grid. - Header dokumen akad memakai logo biru `#0B57D0` setinggi dua baris teks `Vworks Student Venture` tebal biru dan dirapatkan di sebelahnya. Di kanan header, nama PT Vworks dan slogan tampil tebal biru; alamat maksimal dua baris dan nomor telepon memakai ukuran kecil yang sama, berwarna hitam, dengan tata letak rata kanan bergaya Google Sans. - **Dokumen Akad (`.docx`) & Penerbitan NIS:** setelah `pricingStatus` minimal `VERIFIED` dan rincian biaya lengkap, staf dapat meninjau pratinjau dokumen (`GET /api/admin/applications/[id]/akad` via `renderAkadPreviewHtml`, yang membaca isi dan struktur DOCX template) atau menerbitkan dokumen akad (`issueAkadDocument`). **Mode draft vs final:** sebelum penerbitan, route (pratinjau HTML maupun `?mode=docx`) membangun DOCX draft — nomor kontrak `DRAFT — <urutan4>/WKL[-JAL]-JPN/VSV-WSB/<romawi>/<tahun>`, notis paragraf `DRAFT — Dokumen pratinjau. Isi semua bagian dalam tanda [ ] sebelum ditandatangani.`, dan **watermark `DRAFT`** (VML rotasi 315° di `word/header1.xml` DOCX + `<div class="doc-draft-mark">` pada HTML pratinjau, berputar −31,5°); `issueAkadDocument` membangun final (notis dihapus, tanpa watermark) dan route selanjutnya menyajikan berkas final tersimpan dari Drive. Kalimat tanggal mulai di kedua template (`Mulai : Tanggal [tanggal], bulan pertama setelah keberangkatan ke Jepang`) kini berbunyi `mulai dibayar ketika siswa sudah menerima gaji kedua di negara tujuan`, paragraf saksi Dana Keberangkatan terisi `Mitra Venturego (LPK)` bila `lpkWitnessName` kosong (atau `LPK <mitra> — <nama>` bila diisi), DOCX Wakalah memuat heading `Wali/Orang Tua Siswa` setelah `Mengetahui dan menyetujui:`, dan Lampiran A Wakalah tanpa baris header `NAFAQAH`/`UJRAH` maupun baris `Dibayarkan ke LPK (invoice)` — 3 baris layanan Nafaqah digabung lewat `w:vMerge` (penerima `LPK Mitra Venturego`, satu nominal `Rp<nafaqahTotal>`). Tampilan DOCX kini memakai ukuran font turun 2pt (paragraf 9→7pt, default 10→8pt), kop surat logo VentureGo + blok teks 2 baris `Vworks` / `Student Venture` (Raleway tebal 12pt; teks kedua `LPK VentureGo.id · PT Vworks Kolaborasi Bersama` dan garis biru dihapus), ruang tanda tangan bertambah (5 paragraf kosong di bawah nama pada sel baris terakhir ketiga tabel tanda tangan), 5 paragraf kosong per sel pada baris tanda tangan kedua tabel Lampiran C (Penyerah/Penerima), dan kotak centang Lampiran C diperlebar jadi `[          ]`. Saat diterbitkan, server menerbitkan **NIS** (`VSV-{urutan4}-{tahun}`), membentuk nomor dokumen `<urutan4>/WKL-JPN/VSV-WSB/<romawi>/<tahun>` (Dana Keberangkatan) atau `<urutan4>/WKL-JAL-JPN/VSV-WSB/<romawi>/<tahun>` (Full Cover) yang selaras dengan urutan NIS, mengisi placeholder identitas dan Lampiran A (rincian pembayaran; Full Cover menampilkan invoice LPK, uang saku, Ujrah, dan Ju’alah), baris jadwal angsuran Dana Keberangkatan (nominal tiap angsuran dan sisa kewajiban terisi, tetapi **kolom tanggal jatuh tempo dibiarkan kosong**; kalimat tanggal mulai kini teks tetap `mulai dibayar ketika siswa sudah menerima gaji kedua di negara tujuan` tanpa slot tanggal), serta tabel lampiran tanda terima dokumen berisi daftar tetap persyaratan dokumen asli (Akta Kelahiran, Kartu Keluarga, Ijazah SD/MI, Ijazah SMP/MTs/SLTP, Ijazah SMA/MA/SLTA) dengan kolom Asli/Fotokopi, Jumlah, dan Keterangan dikosongkan untuk dicentang saat akad, mengunggah berkas `.docx` ke folder Drive pengajuan, menyimpan metadata `financialPlan.akadDocument`, mengisi `finalAgreementReference` otomatis dengan nomor dokumen bila sebelumnya kosong, dan mengunci rincian biaya (`saveFinancialPlan` & `approveApplicationPricing` ditolak; transisi `setApplicationPricingAgreed` ke `AGREED` tetap diizinkan setelah siswa menyetujui penawaran).
- **PDF akad final:** setelah `pricingStatus: AGREED`, staf dapat mengunggah PDF bertanda tangan melalui tab Persetujuan & Akad. Server membatasi PDF maksimal 4 MB, memeriksa signature berkas, menyimpan ke folder Drive privat pengajuan dengan nama `Akad Wakalah bil Ujrah - <Nama Pemohon>.pdf`, lalu menambahkan metadata `agreementPdf` ke aplikasi. Unggah PDF akad bertanda tangan basah tetap dilakukan sesudahnya untuk melengkapi arsip. Perubahan status manual ke `ACTIVE` juga menjalankan promosi folder. Operasi Drive bersifat terbaik-usaha dan tidak menggagalkan penerbitan/status.

`firestore.rules` **deny-all** — semua baca/tulis via Admin SDK di server. Tombol Tolak & Hapus hanya menghapus satu dokumen pengajuan non-legacy dari `applications`; record pembayaran, berkas Drive, profil/NIS, dan counter tidak dihapus. Pembayaran yang lunas setelah pengajuan dihapus tetap dicatat ke `payments`, tanpa menulis kembali ke aplikasi yang sudah dihapus.

**Entri dokumen** (`applications.documents[]`): `{documentType, status: NOT_UPLOADED\|UPLOADED\|VERIFIED\|REVISION_REQUIRED, fileId?, fileName?, mimeType?, size?}` — `fileId` adalah ID Google Drive.

## 8. Catatan Kondisi Saat Ini (Known Caveats)

Daftar ini **harus ikut diperbarui** saat caveat-nya diselesaikan:

- **Pembayaran kontrak LGC yang tidak memiliki `installmentNumber` belum bisa direkonsiliasi ke cicilan tertentu.** Nominal transaksi `PAID` tetap dihitung pada total terbayar, tetapi status dan realisasi per cicilan hanya memakai alokasi yang tersedia atau `paidInstallments`; aplikasi menampilkannya sebagai belum dialokasikan dan tidak melakukan tebakan/migrasi otomatis.

1. **Wizard hanya memuat scan KTP** — scan KTP wajib dipilih di langkah Data diri dan diunggah ke Drive bersamaan saat submit; dokumen lain diunggah setelah submit di `/dashboard/unggah-berkas` dan pengajuan baru selalu memulai slot lain `NOT_UPLOADED`.
2. **Hanya Scan KTP yang memblokir submit** — penanda `*` pada dokumen wajib lain (Pas Foto, Scan KK, Ijazah, KTP/wali Full Cover) tetap penanda tampilan di `/dashboard/unggah-berkas` dan diverifikasi staf setelahnya; cek `required` tidak lagi dijalankan saat submit. Validasi server mengwajibkan Scan KTP di kedua produk (`Dokumen Scan KTP wajib diunggah.`).
3. **Ganti dokumen tidak menghapus file lama** di Drive (file lama tetap tersimpan di folder yang sama).
4. **VIP belum punya pendaftaran & kontrak** — staf mencatat mitra dan transaksi di `/admin` → Mitra VIP; belum ada pendaftaran mitra dari aplikasi, kontrak/akad mitra, top-up Xendit, maupun laporan PDF bulanan. Rencana ada di `docs/usulan/2026-11-vip-pendaftaran-dan-akad.md` (pendaftaran rinci, kontrak seperti siswa, akad diperbarui sesuai fikih muamalah).
5. **Kuota daftar admin maks 500 pengajuan & 500 pembayaran terbaru** — pencarian dan filter berjalan di klien atas 500 pengajuan terbaru.
6. **Tahap 5 (Pencairan dana)** pada `Alur progress` tidak pernah jadi tahap `SEKARANG`.
7. **Tidak ada halaman login admin** — staf masuk lewat `Masuk dengan Google` di welcome `/`; allowlist & cookie tetap berlaku. `vworksofficial@gmail.com` dan `demo.admin@venturego.id` terdaftar di `isStaffEmail`.
8. **Record lama milik akun anonim tidak bisa diakses pemohon** setelah migrasi ke Google; admin masih melihatnya di `/admin`, tetapi tidak ada jalur klaim karena email anonim tidak tersimpan. Jangan hapus record tersebut.
9. **Kredensial akun demo ada di `src/lib/demo-accounts.json`** (`demo.user@venturego.id` / `UserDemo123!` dan `demo.admin@venturego.id` / `AdminDemo123!`), tetapi **tidak ada lagi tombol demo** di halaman awal (semua mode hanya `Masuk dengan Google`). Akun demo masih bisa dipakai lewat script seed bila diperlukan.
10. **NIS hanya diterbitkan saat staf menerbitkan dokumen akad** (`issueAkadDocument` di tab `Draft Akad` pada `/admin`) melalui transaksi Firestore pada `studentProfiles` dan `systemCounters` — urutan 4 digit NIS yang sama langsung dipakai untuk membentuk nomor dokumen akad (`<urutan4>/WKL[-JAL]-JPN/VSV-WSB/<romawi>/<tahun>`). Penerbitan akad langsung mengubah status pengajuan ke `ACTIVE`; promosi folder dan transisi manual ke status tersebut hanya membaca NIS yang sudah ada secara read-only (`getExistingStudentNumber`). Penerbitan otomatis saat membuka halaman Profil/Kartu tetap dihapus (read-only). NIS lama yang sudah terbit tetap tampil. Tidak perlu migrasi massal dokumen pengajuan; nomor yang sudah diterbitkan tetap sama untuk UID tersebut.
11. **PDF akad final belum tersedia sampai staf mengunggah dokumen bertanda tangan** dari tab Persetujuan & Akad di `/admin` setelah biaya berstatus `Disepakati`.
12. **Mode development terhubung langsung ke project Firebase Cloud di `.env.local`** (tanpa memerlukan emulator lokal). Untuk login Google di lokal, gunakan `http://localhost:3000` (akses ke `127.0.0.1` otomatis dialihkan ke `localhost` karena Firebase hanya mengizinkan domain `localhost` secara bawaan). Login Google langsung butuh `NEXT_PUBLIC_GOOGLE_CLIENT_ID` dan origin `http://localhost:3000` terdaftar di _Authorized JavaScript origins_ OAuth client; tanpa env itu dipakai popup Firebase.
13. **Mengganti PDF akad mengaitkan file baru ke aplikasi; file versi sebelumnya tidak dihapus dari Google Drive** agar arsip lama tidak terhapus. Karena nama file kini standar (`Akad Wakalah bil Ujrah - <Nama Pemohon>.pdf`), versi lama dan baru dapat bernama sama dan dibedakan oleh waktu ubah di Drive.
14. **Folder & file lama tidak dimigrasi massal** — hanya root yang di-rename in-place; folder draft lama (format `<Nama> · <uid6>`) dan nama file lama tetap seperti aslinya sampai pengajuan terkait mencapai `ACTIVE` (saat itu folder di-rename `<NIS> - <Nama>`, diwarnai hijau, dan seluruh file di dalamnya ikut di-rename ke pola standar).
15. Halaman 404 (`not-found`) masih berbahasa Inggris.
16. **Penerusan webhook bersama akun Xendit** — `trm-` (Turrima) dan `vsv-` (36 kontrak siswa di app VentureGo versi lama, database terpisah) diteruskan, bukan diproses. Data kontrak lama **belum dimigrasi** ke Firestore; selama itu app lama harus tetap hidup di alamat `vercel.app`-nya. `XENDIT_CALLBACK_TOKEN` harus sama di semua app yang berbagi akun Xendit.
17. **Kebijakan Privasi & Syarat Layanan masih draf** — perlu ditinjau legal/DPS (nama badan hukum, email layanan) sebelum dipakai untuk verifikasi merek Google atau toko aplikasi.
18. **Pengajuan Dana Keberangkatan lama menyimpan struktur Nafaqah/Ujrah format lama** — server kini menurunkan ulang rincian dari principal + invoice LPK, sehingga record lama yang belum disimpan ulang ditolak saat `Setujui` / `Tandai Disepakati` / penerbitan dokumen dengan pesan yang mengarahkan staf ke tab Draft Akad. Tidak ada migrasi massal: struktur lama otomatis terganti saat staf menyimpan rincian berikutnya (satu kali simpan), dan dokumen akad yang sudah terbit tidak berubah. Field `financialPlan.principal` bersifat aditif (baru diisi saat disetujui/simpan).
